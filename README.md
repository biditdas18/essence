# Essence: A Personal Embedding Cluster Framework
## for Depth-Optimized Recommendations

**The primary contribution of Essence is recovering niche
content that matches a user's idiosyncratic taste,
independent of popularity metrics.**

### What Essence Does

Essence operates exclusively within a single user's
engagement history. No cross-user data is consulted at
any stage. A user's item history is embedded using a
pre-trained sentence encoder (all-MiniLM-L6-v2) and
clustered into K=3 semantic centroids via K-means.
Recommendations are generated by selecting the active
centroid aligned with the user's recent context and
retrieving semantically similar unseen items by cosine
similarity.

The peer-isolation property (no cross-user interaction
graph consulted at any stage) is not merely a privacy
consideration. It is a depth requirement. Crowd signals
approximate preferences at the genre level. Peer-isolation
enables modelling at the latent feature level: the specific
combination of characteristics a user responds to,
independent of how other users categorise those
characteristics. Discovery becomes mathematical,
not accidental. We describe the resulting objective as
depth-optimized: the goal is to retrieve items deep in a
user's long-tail interest space, rather than to maximise
aggregate engagement on broadly popular items.

### How Essence Differs from MIND, ComiRec, and CF

| Property | CF | MIND | ComiRec | **Essence** |
|---|---|---|---|---|
| Cross-user data required | Yes | Yes | Yes | **No** |
| Multiple interest profiles | No | Yes | Yes | **Yes** |
| Model training required | Yes | Yes | Yes | **No** |
| Long-tail item recovery | Poor | Poor | Poor | **Yes** |
| No cross-user data required | No | No | No | **Yes** |
| Optimised for popular items | Yes | Yes | Yes | **No** |
| **Optimised for niche items** | No | No | No | **Yes** |
| Embedding source | Co-occurrence | Co-occurrence | Co-occurrence | **Item metadata** |

MIND (Li et al., CIKM 2019) and ComiRec (Cen et al., RecSys 2020) share
Essence's multi-interest intuition but require population-level interaction
graphs for training. Their entries above reflect architectural expectations;
they are not empirically evaluated in this work. A direct empirical
comparison is planned as future work.

**Essence is not competing with MIND or ComiRec on their
own terms. It is solving a different problem: surfacing
niche content that matches idiosyncratic individual taste,
using only that user's own history, with no popularity
signal involved.**

### Experimental Results

All systems evaluated under full-catalog ranking protocol
(no negative sampling). Recall@K is computed as
`|hits ∩ test| / |test|` (standard definition).
Absolute recall values are low by construction — the
meaningful signal is the relative pattern across systems
under identical conditions. LT-Recall = same metric
restricted to singleton train items (interacted with by
exactly 1 user in the training split); users with no
singleton test items are excluded from the LT-Recall
average.

---

**Table 1 — Last.fm-1K (Music)**
99 users · 22,767 catalog items · 16,761 singleton items (73.6%)
Chronological 80/20 split · standard Recall@K
Embeddings: item metadata (track name + artist name)

| System | Recall@10 | LT-Recall@10 | LT / Content |
|---|---|---|---|
| Random | 0.0001 | 0.0000 | — |
| Popularity | 0.0023 | 0.0000 | — |
| CF (ItemKNN) | 0.0018 | 0.0000 | — |
| Content (Avg Emb) | 0.0038 | 0.0029 | 1.00x |
| **Essence (K=3)** | **0.0119** | **0.0059** | **2.01x** |

Popularity and CF (ItemKNN) are separated baselines:
Popularity is non-personalized frequency ranking;
CF (ItemKNN) uses cosine similarity over the user-item
co-occurrence matrix (Sarwar et al., WWW 2001).
Popularity achieves zero long-tail recall by construction.
CF (ItemKNN) also achieves zero long-tail recall on this
sparse dataset: co-occurrence signal is insufficient to
surface singleton items when only 99 users are present,
and under deterministic tie-breaking CF recovers none.
Essence achieves 2.01x the long-tail recall of the
content baseline.

---

**Table 2 — Amazon Books (E-commerce, Metadata Embeddings)**
2,000 users · 61,727 catalog items · 42,878 singleton items (69.5%)
Chronological 80/20 split · standard Recall@K
Embeddings: item metadata (title + author name)
Cross-domain replication of Table 1.

| System | Recall@10 | LT-Recall@10 | LT / Content |
|---|---|---|---|
| Random | 0.0001 | 0.0000 | — |
| Popularity | 0.0021 | 0.0000 | — |
| CF (ItemKNN) | 0.0031 | 0.0137 | 1.11x |
| Content (Avg Emb) | 0.0173 | 0.0124 | 1.00x |
| **Essence (K=3)** | **0.0221** | **0.0197** | **1.59x** |

The pattern replicates. Popularity achieves zero long-tail
recall again. CF (ItemKNN) recovers marginal long-tail recall
here (0.0137, 1.11x Content): with 2,000 users, co-occurrence
signal becomes sufficient to surface some low-interaction items.
CF's long-tail recovery is thus density-dependent — zero on the
sparse Last.fm-1K (matching Popularity), marginal on the denser
Amazon Books. Essence leads on long-tail recall regardless of
dataset density (2.01x on Last.fm-1K, 1.59x on Amazon Books)
and also leads on overall Recall@10 among personalized methods.

---

**Active-cluster-selection ablation (Last.fm-1K):**
Replacing recency-based centroid selection (mean of last 10 train
items chronologically) with mean-of-all-train selection collapses
Essence toward the Content baseline with no differentiation
benefit (LT-Recall 0.0005 vs 0.0059 for recency). The recency
mechanism, not the clustering step alone, is responsible for
the long-tail advantage. Ablation verified on Last.fm-1K only.

**User-review embedding experiment (Amazon Books, Pass 2):**
As a secondary experiment, taste profiles were built from
user-authored review text rather than item metadata, with
candidates still scored by metadata embeddings. Absolute
recall degrades substantially (embedding-space mismatch +
review noise), but Essence's relative advantage over Content
persists: 2.83x LT-Recall ratio in Pass 2 vs 1.59x in Pass 1,
suggesting the K-means clustering mechanism extracts usable
interest structure even under degraded input.

### Changelog from original SSRN posting

Three methodological corrections were applied between the
original SSRN preprint and the current version, all in
the direction of a harder and more standard evaluation.
The core comparative finding is unchanged: Essence
consistently outperforms Content on long-tail recall
across both datasets, and Popularity achieves zero
long-tail recall in every configuration.

1. **CF baseline replaced.** The original "CF Baseline"
   was global popularity ranking, not collaborative
   filtering. It has been renamed Popularity and a real
   ItemKNN CF baseline (item-item cosine similarity over
   the user-item matrix) has been added as a separate
   system.

2. **Train/test split changed to chronological.** The
   original evaluation used random 80/20 hold-out per
   user. This was inconsistent with the active-cluster
   selection mechanism, which selects the centroid
   nearest to the user's most recent interactions.
   Both datasets now use a chronological 80/20 split
   (first 80% by timestamp = train, last 20% = test),
   making the recency mechanism internally consistent
   with the evaluation protocol.

3. **Recall@K metric corrected.** The original
   implementation used `hits / min(|test|, k)` as the
   denominator, which inflates recall when test sets
   are large (|test| >> k). The standard denominator
   `hits / |test|` is now used throughout. Absolute
   recall values are lower as a direct consequence —
   this is expected and correct.

### Additional Analyses (post-paper)

The following were added after the paper's tables were finalized — new
recency-based baselines, a statistically direct comparison test, K/seed
sensitivity, and an artist/author shortcut check. **These are not yet
reflected in `paper/essence_paper_v2.tex`.**

**New baselines.** Three recency-based baselines were added to
`models/recommenders.py` (`last_item_recommend`, `avg_last10_recommend`,
`recency_weighted_recommend`) and to the Amazon per-user script
(`experiments/amazon_books/evaluate_amazon_peruser.py`), scored the same
way as Content/Essence. They now run by default alongside the original
5 systems — no separate command needed, see `evaluation_results_v6.csv`
(Last.fm, 8 systems) and the regenerated `results_amazon_peruser.csv`
(Amazon, 8 systems). `essence_recommend` also gained an optional `seed`
parameter (default 42, unchanged behavior) to support the seed-variance
analysis below.

Headline finding: on both datasets, the recency baselines are competitive
with or beat Essence on raw Recall@10 (e.g. Last-Item beats Essence on
Amazon: 0.0311 vs 0.0221). On **LT-Recall@10** — the paper's headline
metric — Essence's advantage over the *original* baselines (Random,
Popularity, CF, Content) holds, and its lead over the new recency
baselines specifically is not statistically significant either way on
Amazon (see paired bootstrap below), but Last.fm's LT-Recall gap between
Essence and Recency-Weighted only narrows to significance at the 90%
level (P(diff>0)=0.020, i.e. Recency-Weighted wins with 98% confidence at
n=99 users). This is a real result the paper does not yet address.

**Paired bootstrap** (`evaluation/paired_bootstrap.py`) replaces
eyeballing independent per-system CIs (`analyze_cis.py`) with a direct
test on the paired per-user Essence-vs-baseline difference:

```bash
python evaluation/paired_bootstrap.py \
    --input results/evaluation_results_v6.csv \
    --label "Last.fm-1K" \
    --output results/paired_bootstrap_lastfm.csv

python evaluation/paired_bootstrap.py \
    --input experiments/amazon_books/results_amazon_peruser.csv \
    --label "Amazon Books (Pass 1)" \
    --output results/paired_bootstrap_amazon.csv
```

**K-sensitivity + seed variance** (Essence at K=2..5, and K=3 across 10
K-means seeds):

```bash
python evaluation/sensitivity.py                        # Last.fm -> results/sensitivity_results.csv
python experiments/amazon_books/sensitivity_amazon.py   # Amazon  -> results/sensitivity_results_amazon.csv
```

On Last.fm, K=4/5 clearly outperform the paper's K=3 (Recall@10 0.0239
and 0.0251 vs 0.0119), a much bigger swing than the seed-variance noise
floor (std 0.0011). On Amazon the K-sweep is much flatter (0.0214 to
0.0242 across K=2..5) and close to its own seed-variance std (0.0009).
K=3 was not re-validated as optimal for either dataset — **flagging this
for your attention, not changing the paper's K=3 default.**

**Artist/author shortcut check** — is Essence just recommending items by
artists/authors already in the user's active cluster?

```bash
python evaluation/shortcut_check.py                       # Last.fm -> results/shortcut_analysis.csv
python experiments/amazon_books/shortcut_check_amazon.py  # Amazon  -> results/shortcut_analysis_amazon.csv
```

On both datasets, ~20% of Essence's top-10 recs share an artist/author
with the active cluster (Last.fm 20.6%, Amazon 19.8%) — not the majority
of recommendations. But excluding those same-artist/author candidates
collapses both metrics sharply (Last.fm Recall@10 0.0119→0.0014,
LT-Recall@10 0.0059→0.0005; Amazon Recall@10 0.0221→0.0073,
LT-Recall@10 0.0197→0.0080). The same-artist minority of recommendations
accounts for a disproportionate share of Essence's actual hits on both
datasets. **Flagging this as a real finding, not editing the paper.**

### Averaging convention audit

Every eval/analysis script in this repo (`evaluate.py`, both Amazon
per-user scripts, `sensitivity.py`/`sensitivity_amazon.py`,
`shortcut_check.py`/`shortcut_check_amazon.py`, and
`experiments/mind_comirec/train.py`) computes Recall@K / LT-Recall@K as
a **per-user ratio, then arithmetic-means across users (macro-average)**
— none of them pool total hits over total opportunities globally
(micro-average) before dividing. This was verified by reading each
script's metric function and its aggregation call directly, not assumed.
MIND/ComiRec don't have their own copy of the metric logic at all — they
import `recall_at_k`/`long_tail_recall_at_k` straight from
`evaluation/evaluate.py`, so there's no way for them to have drifted from
the convention used by every other baseline. See `recall_at_k`'s
docstring in `evaluation/evaluate.py` for the full note.

### Cold-start vs. singleton long-tail: a scope boundary, not a contradiction

A popularity-decile breakdown on Amazon Books (10 equal-item-count
buckets by train-set interaction count, rarest to most popular; see
`results/popularity_decile_recall.csv`) found Essence trailing
Last-Item and Recency-Weighted at deciles 1 and 2 — statistically real
per a dedicated paired-bootstrap + BH-FDR + BCa check
(`results/decile_significance_check.csv`, `results/decile_bca_check.csv`):
Essence loses to Last-Item at both deciles (survives FDR correction)
and to Recency-Weighted at decile 2 (survives FDR; the decile-1 version
of this comparison is significant at raw p but does not survive
correction).

This does **not** contradict the paper's headline LT-Recall@10 claim
(Essence beats Content/CF/Popularity on singleton-item recall), because
the two are measuring almost entirely different item populations
(`results/longtail_definition_reconciliation.csv`):

- **Decile 1 contains zero singleton items.** It's entirely items with
  *zero* train interactions — true cold-start items, rarer than
  singletons by construction (popularity 0 < 1). Decile 2 contains only
  3.6% of the catalog's 42,878 singletons. The singleton population
  (the paper's long-tail definition) is concentrated in **deciles 3–9**
  (86% of all singletons).
- **100% of Essence's actual LT-Recall@10 hits come from deciles 3–9**
  (37% from decile 9 alone) — **zero** from deciles 1 or 2.

So: Essence's headline long-tail win is real and comes from
moderately-rare-but-observed items (deciles 3–9). Essence's weakness at
true cold-start items (deciles 1–2, zero or near-zero training signal)
is also real, and is a genuine scope boundary on the long-tail claim —
the paper's "long-tail recovery" result should be read as covering
observed-but-rare items, not unobserved cold-start items, where the
simpler recency baselines currently do better. Neither finding
invalidates the other; they're about different items.

### Reproducing the Results

All results are fully deterministic. Random baselines use
MD5-based per-user seeds (independent of PYTHONHASHSEED).
CF tie-breaking uses lexicographic stable sort (score desc,
item index asc). Re-running the evaluation scripts produces
the exact numbers reported in the paper.

#### Script → paper table map

| Paper table | Generator script | Output file(s) |
|---|---|---|
| Table 3 — Last.fm-1K | `evaluation/evaluate.py --output evaluation_results_v5.csv` | `results/evaluation_results_v5.csv` |
| Table 4 — Amazon Books (Pass 1) | `experiments/amazon_books/evaluate_amazon_peruser.py` | `results_amazon_peruser.csv` (aggregate ≡ `results_amazon_v4.csv`) |
| CI table (tab:cis) | `analyze_cis.py` | reads the two per-user CSVs above |
| Table 6 — Amazon Books (Pass 2) | `experiments/amazon_books/evaluate_amazon_pass2_peruser.py` | `results_amazon_pass2_peruser.csv` |

Amazon scripts load cached embeddings from `data/amazon_processed/`
(`embeddings_metadata.pkl` for the candidate matrix in both passes;
`embeddings_user_review.pkl` additionally for Pass-2 profile vectors).
Both scripts are deterministic end-to-end: KMeans `random_state=42`,
MD5-based per-user random seeds, `np.lexsort` tie-breaking.

The file `deprecated/evaluate_amazon_SUPERSEDED.py` is an early script
where the system labeled "CF" was a popularity baseline, not ItemKNN.
Its results do not correspond to any table in the paper; see
`deprecated/README.md`.

- Python 3.11+
- macOS, Linux, or Windows
- ~4 GB disk space for Amazon data (~10 GB temporary during download)

#### Last.fm-1K Experiment (Music)

```bash
# 1. Download and preprocess (chronological split)
python data/preprocess.py

# 2. Generate item embeddings (all-MiniLM-L6-v2; ~2 min)
#    Output: embeddings/item_embeddings.pkl  (not committed — regenerated here)
python embeddings/generate_embeddings.py

# 3. Run all systems and evaluate (now 8: the 5 paper systems + 3 new baselines)
python evaluation/evaluate.py --users 99 --K 3 --M 10 --output evaluation_results_v5.csv
```

Results will print to console; the 5 paper-system rows (Random,
Popularity, CF (ItemKNN), Content (Avg Emb), Essence (K=3)) match Table 3
exactly. The command now also produces Last-Item / Avg-Last-10 /
Recency-Weighted rows in the same file (post-paper baselines — see
"Additional Analyses" above); this doesn't change the 5 published numbers.
